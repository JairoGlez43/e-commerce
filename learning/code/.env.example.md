# `.env.example`

> **Qué es:** la plantilla de las variables de entorno del proyecto · **Lo decidió:**
> [spec 0007](../../docs/specs/0007-whatsapp-order.md) (`WHATSAPP_NUMBER`) y
> [spec 0013](../../docs/specs/0013-catalog-data-online.md) (`SUPABASE_URL`,
> `SUPABASE_PUBLISHABLE_KEY`) · **Lo usan:** las personas que montan el proyecto (tú, Vercel) ·
> **Usa:** nada

## Para qué sirve

El proyecto necesita datos que no deben estar en el código: el número de WhatsApp que recibe los
pedidos y, desde la spec 0013, la dirección y la clave del proyecto de
[Supabase](glosario.md#supabase) de donde el build lee el catálogo. Esos datos van en un archivo
`.env`, que git **ignora** (está en `.gitignore`), así que nunca se suben a GitHub. Pero si `.env`
no se sube, alguien que clone el repo no sabría qué poner. Para eso está `.env.example`: **sí** se
sube, con los mismos nombres pero valores falsos, y explica el formato. Es la costumbre habitual
en proyectos de Node.

## El código, por partes

```bash
# Copy this file to .env (gitignored) and put the real values there. Never commit .env.
```

- `#` empieza un comentario en este formato. Dice: "Copia este archivo a `.env` (que git ignora)
  y pon ahí los valores reales. Nunca subas `.env` al repo."

```bash
# WhatsApp number that receives orders (spec 0007): international format, digits only,
# no + or spaces. Example: Cuba is 53 + 8 digits. This one is fake.
WHATSAPP_NUMBER=5350000000
```

- El comentario: "Número de WhatsApp que recibe los pedidos (spec 0007): formato internacional,
  solo dígitos, sin `+` ni espacios. Ejemplo: Cuba es 53 + 8 dígitos. Este es falso."
- `WHATSAPP_NUMBER=5350000000`: el formato de cada línea es `NOMBRE=valor`, sin espacios
  alrededor del `=` y sin comillas. El nombre es el que lee `getWhatsAppNumber()` con
  `import.meta.env.WHATSAPP_NUMBER`. El valor es **falso** a propósito.

```bash
# Supabase project the build reads the catalog from (spec 0013). Dashboard > Project Settings.
# The project URL only: no /rest/v1 and no trailing slash. These values are fake.
SUPABASE_URL=https://abcdefghijklmnop.supabase.co
```

- El comentario: "Proyecto de Supabase del que el build lee el catálogo (spec 0013). En el panel:
  *Project Settings*. Solo la URL del proyecto: sin `/rest/v1` y sin barra final. Estos valores
  son falsos."
- `SUPABASE_URL=https://abcdefghijklmnop.supabase.co`: la dirección del proyecto. La parte antes
  de `.supabase.co` es el código único de cada proyecto; aquí es inventado. Si la escribes con
  `/` al final o con `/rest/v1`, `getConfig()` en [`src/lib/supabase.ts`](src/lib/supabase.ts.md)
  para el build con un mensaje que lo explica.

```bash
# The publishable key (sb_publishable_...), never the secret key (sb_secret_...).
SUPABASE_PUBLISHABLE_KEY=sb_publishable_example
```

- El comentario: "La clave publishable (`sb_publishable_…`), nunca la clave secreta
  (`sb_secret_…`)."
- `SUPABASE_PUBLISHABLE_KEY=sb_publishable_example`: la
  [clave publishable](glosario.md#clave-publishable). Es pública por diseño (solo puede leer lo que
  permiten las reglas de la base de datos), pero se guarda fuera del repo igual que el número. Si
  alguien pega por error la secreta, el build la reconoce por su principio `sb_secret_` y se para.
- Estas dos variables solo se usan en el build: no llegan nunca a las páginas que descarga el
  cliente (spec 0013, AC7).

## Cómo se conecta

- **Tú:** copias este archivo como `.env` en la raíz del proyecto y cambias los valores por los
  tuyos. `pnpm dev` y `pnpm build` cargan `.env` solos. Desde la spec 0013, los dos comandos
  necesitan además internet, porque leen el catálogo de Supabase.
- **Vercel:** las mismas tres variables se ponen en la configuración del proyecto en Vercel
  (entornos *Production* y *Preview*), porque allí no hay `.env`.
- **Claude:** nunca lee ni muestra `.env` (regla de `AGENTS.md`). Para sus pruebas pasa los
  valores falsos en el propio comando: `WHATSAPP_NUMBER=5355555555 pnpm build`.
- **El código:** [`src/lib/whatsapp.ts`](src/lib/whatsapp.ts.md) lee el número,
  [`src/lib/supabase.ts`](src/lib/supabase.ts.md) lee las dos de Supabase y
  [`src/env.d.ts`](src/env.d.ts.md) declara sus tipos.

## Prueba tú

Crea tu `.env` (si aún no lo tienes):

1. En el explorador de VS Code, clic derecho sobre `.env.example` → Copiar, y pégalo en la raíz.
   Renombra la copia a `.env`.
2. Cambia `5350000000` por tu número: código de país + número, solo dígitos (por ejemplo, un
   móvil de Puerto Rico sería `1787` + 7 dígitos).
3. Cambia `SUPABASE_URL` y `SUPABASE_PUBLISHABLE_KEY` por los de tu proyecto: en el panel de
   Supabase, *Project Settings* (la URL del proyecto y, en las claves de la API, la *publishable*).
4. Ejecuta `pnpm build`: termina bien. En la pestaña de Git de VS Code, `.env` **no** aparece
   como cambio, porque git lo ignora.
5. Para deshacer, basta con borrar `.env`; el próximo `pnpm build` fallará pidiendo las
   variables. La primera que echa en falta es `SUPABASE_URL`, porque el build lee los datos
   (paso `[content] Syncing content`) antes de generar las páginas que usan el número.
